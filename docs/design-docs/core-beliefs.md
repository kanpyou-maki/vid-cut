# 中核的信念 — コーディング原則とエージェントファースト設計

このリポジトリが前提とする設計思想と実装原則を記録する。

## エージェントファースト原則

1. **認識可能性が最優先**: エージェントがコンテキスト内でアクセスできないものは存在しないと同じ。Google Docs や Slack のスレッドに存在する知識はリポジトリに取り込むこと
2. **地図と百科事典を分ける**: エントリポイント（CLAUDE.md）は地図として機能し、詳細情報は個別ファイルへ委譲する
3. **機械的強制が文書的記述に勝る**: 規則はドキュメントに書くだけでなく、リンターや構造テストで自動強制する
4. **計画は一級成果物**: 実行プランはリポジトリ内でバージョン管理し、セッション横断で追跡可能にする
5. **GC を常に動かす**: 技術的負債は複利で膨らむ。定期的な小さなクリーンアップで防ぐ
6. **コードは Claude が書く、人間は意図を明確にしてレビューする**: 理想としてエージェントが実装を担い、人間はタスクの優先付け・要件の言語化・成果の検証に集中する
7. **エンジニアの主役割は「環境設計」**: コードを書くことではなく、エージェントが有用な作業をできるツール・フィードバックループ・ガードレールを設計・整備することが人間の仕事である
8. **摩擦は改善シグナル**: エージェントが苦戦しているとき、答えは「もっと頑張れ」ではない。不足しているツール・ガードレール・ドキュメントを特定し、リポジトリ自体を改善する
9. **規律はスキャフォールディングに現れる**: ソフトウェアの品質を保つ規律は、コードそのものよりもツール・抽象化・フィードバックループ（スキャフォールディング）に現れる。このリポジトリ自体がその規律の体現である

## コーディング原則

| 原則 | 詳細 |
|------|------|
| **テスト先行** | 実装コードの前に必ず失敗するテストを書く |
| **小さなファイル** | 1ファイルは 300行以内を目安にする |
| **イミュータビリティ** | 直接変更より spread / map / filter を優先する |
| **デバッグコード禁止** | `console.log` をタスク完了前に削除する |
| **クエリのパラメータ化** | ユーザー入力を SQL やシェルコマンドに連結しない |
| **シークレットは環境変数** | 秘密情報をコードにハードコードしない |

## 依存関係の選択基準

- **「退屈な」技術を選ぶ**（構成可能性・API 安定性・訓練データでの表現度が高い）— エージェントは学習データに多く登場する技術をより正確にモデル化できる。最先端の技術ほどエージェントの推論精度が下がる
- 外部ライブラリの不透明な動作を避けるため、小規模な機能は自前実装を検討する — 自前実装はリポジトリ内で完全に検査・変更・テスト可能
- 自前実装にはテストカバレッジ 80% 以上を求める

## 「リポジトリに書け」の原則

エージェントの観点から見れば、**コンテキスト内でアクセスできないものは存在しないも同然**。

以下のものはすべてリポジトリに取り込むこと:

| 外部に存在しがちな知識 | リポジトリ内の置き場所 |
|----------------------|---------------------|
| アーキテクチャ上の合意・判断 | `docs/adr/` |
| 設計の背景・制約・トレードオフ | `docs/design.md`, `docs/design-docs/` |
| チームの規範・コーディング方針 | `.claude/rules/`, `docs/design-docs/core-beliefs.md` |
| ライブラリ選定の理由 | `docs/adr/` または `docs/design.md` |
| 進行中・完了した計画 | `docs/exec-plans/` |

**判断基準:** 「3か月後に入社する新しいエージェント（または人間）がこれを知る必要があるか？」 → Yes なら今すぐリポジトリに書く

## Claude が生成するものの範囲

このリポジトリにおける Claude の生成範囲と、人間の判断が必要な領域を明確に区分する。

**Claude が自律的に行う:**

| 種類 | 具体例 |
|------|--------|
| 実装 | hooks/ の実装、agents/ の定義、skills/ の内容、rules/ の記述 |
| テスト | test/ の全テスト（TDD） |
| ドキュメント・設計履歴 | ADR の記述（既存決定の記録）、QUALITY_SCORE.md の更新、exec-plans のライフサイクル管理 |
| レビュー | レビューコメントへの返答・修正・再提出 |
| リポジトリ管理 | install.sh の更新、フックのバグ修正 |

**人間の判断が必要:**

| 種類 | 具体例 |
|------|--------|
| 優先順位決定 | 何を次に作るか |
| 新しいアーキテクチャ判断 | 既存 ADR でカバーされていない設計変更 |
| 受け入れ基準の定義 | ユーザーフィードバックをタスク要件に変換する |
| 出荷可否 | ユーザーに届ける最終判断 |

## 自律性レベルとエスカレーション基準

**自律性レベルはハーネスの準備に依存する。** ツール・ガードレール・ドキュメントが整備されているほど、Claude はより大きなタスクを人間なしで完遂できる。整備が不十分な領域では自律度が下がる。

Claude が人間にエスカレーションする基準:

| 状況 | 対応 |
|------|------|
| 同一ステージで 3回連続 BLOCK | 実装アプローチの見直しを人間に相談する |
| 要件が曖昧で複数の解釈が可能 | 進める前に意図を確認する |
| 既存 ADR でカバーされていないアーキテクチャ判断 | 人間に決定を求め、ADR に記録する |
| セキュリティ上の重大な懸念 | 即座に作業を停止し人間に報告する |
| bootstrap/GC が 3回修正しても問題が解消しない | 根本原因を報告して判断を仰ぐ |

それ以外の状況では、Claude は自律的に判断して進める。

## スループット指向のマージ哲学

エージェントのスループットが高い環境では、従来のエンジニアリング常識が逆効果になる場合がある。

| 考え方 | 低スループット環境 | 高スループット（エージェント）環境 |
|--------|----------------|-------------------------------|
| テスト失敗 | マージブロック | 再実行 or フォローアップ PR で対処 |
| PR の期間 | 長期レビュー可 | 短期完了を目指す（長期化はスコープ分割）|
| 不安定なテスト | 修正が先 | フォローアップで並行対処 |
| 修正 vs. 待機 | 待機してレビュー | 修正は安価、待機は高コスト |

**原則:** 修正は安価で、待機は高コスト。ブロックを最小限にし、フォローアップで直す。

**前提:** この哲学はエージェントのスループットが十分に高い場合に成立する。低スループット環境では適用範囲が異なる。

## ルールのエスカレーション原則

ルールの強制には段階がある。同じ違反が繰り返されるたびに、一段上に昇格させる。

```
口頭合意・暗黙知
  ↓ 繰り返し忘れられる
docs/ に記述（なぜそうするかを説明）
  ↓ 繰り返し違反される
agents/ のレビュアーがチェック（review-loop で検出）
  ↓ さらに繰り返される・機械的に検出可能
hooks/ の linter に昇格（ARCH-NNN として自動強制）
```

- **「なぜ」はドキュメントが説明し、「何が違反か」は linter が検出する**
- linter のエラーメッセージには必ず修復手順を含める（エージェントが自律的に修正できるように）
- ドキュメントだけに留まるルールは腐敗する。機械的に検出できるものは機械化する

## 境界は中央管理、自律性はローカル

強制する領域と自由にする領域を明確に区別する。

**中央で強制する（ARCH-001〜006・黄金原則）:**
- ファイルの配置場所
- 依存方向
- CLAUDE.md の行数制限
- docs/ のリンク整合性
- settings.json のフック参照整合性

**エージェントの判断に委ねる:**
- 境界内での実装方法・アルゴリズムの選択
- 変数名・関数名の具体的な命名（命名規則の範囲内で）
- テストケースの追加方法
- リファクタリングの粒度

**生成されたコードは人間のスタイルに合致しなくてよい。** 正しく・保守可能で・将来のエージェントが読めれば十分。スタイルの一貫性は linter が担保する。
