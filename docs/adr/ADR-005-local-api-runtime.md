# ADR-005: ローカル API の実行時の決定（接続・まとめて確定する保存・トークン）

**ステータス:** 提案中
**作成日:** 2026-10-03

## Context（背景）

[ADR-004](./ADR-004-local-app-runtime.md) で、API サーバーと worker プロセスが SQLite のジョブ表で連携する形を決めた。
M6 で API を実装するにあたり、次の 3 点を決める必要があった。

1. SQLite の接続はスレッドをまたげない（`check_same_thread`）。FastAPI は同期の処理をスレッドプールで動かし、依存の準備と本体が別のスレッドになることがある
2. 判定結果と編集状態、レクチャーの置き換えと編集状態とジョブ、のように、複数のリポジトリにまたがる保存がある。
   API が読むようになると、保存の間の状態（編集状態は新しい候補の id、判定結果は古いまま）が画面に見える
3. すべての `/api` で `X-VidCut-Token` ヘッダーを必須にする設計（[Design Doc](../design.md) 3-5-1）だが、`<video>` 要素はヘッダーを付けられない

## Decision（決定）

- **接続はリクエストごとに開いて閉じる。** `check_same_thread=False` で開き、1 つのリクエストの中で直列に使う。リクエストをまたいで共有しない。
  スキーマの移行は起動時に 1 回だけ行う（`bootstrap.build_api` と `Api.services()`）。worker と CLI は、これまでどおり接続を 1 本持つ（`build_app`）
- **複数のリポジトリにまたがる保存は、services が `Atomic`（ports）で囲んで 1 つのトランザクションにする。**
  SQLite の `transaction()` は、既にトランザクションの中ならそれに加わる。確定と取り消しはいちばん外側が行う
- **proxy 動画（`/api/recordings/{id}/proxy`）だけ、トークンを `?token=` のクエリでも受け取る**（ユーザー決定、2026-10-03）。
  ほかの `/api` はヘッダーを必須のままにする。トークンが残らないよう、アクセスログは出さず、応答に `Referrer-Policy: no-referrer` を付ける

## Consequences（結果）

### ポジティブ

- スレッドをまたぐ接続の共有がなく、同時の要求が互いのトランザクションに混ざらない（実物の uvicorn で、並行の読み取り 200 件と、同じ版での同時保存を確認した）
- 途中で失敗しても、編集状態と判定結果、レクチャーとジョブが食い違った状態で残らない
- ブラウザの標準の `<video>`（Range による部分取得とシーク）をそのまま使える

### ネガティブ

- リクエストごとに接続を開く手間がかかる（ローカルのファイルなので 1 ミリ秒未満。画面は 1 秒間隔でポーリングする程度）
- トークンが proxy 動画の URL に入る。ブラウザの履歴には残らない（`<video>` の読み込みは履歴に載らない）が、開発者ツールには表示される。
  トークンは起動ごとに変わるので、漏れても次の起動で無効になる
- services が「どこからどこまでをまとめるか」を知ることになる（リポジトリの実装が同じ接続を使っていることが前提）

## Alternatives Considered（検討した代替案）

### 案 A: 接続を 1 本にして、ロックで直列にする

実装は小さいが、すべての要求が 1 列に並ぶ。長い読み取り（レクチャーの詳細）の間、進捗の取得が待たされる。採用しない。

### 案 B: スレッドごとに接続を持つ（thread-local）

接続を開く回数は減るが、スレッドプールのスレッドがいつ終わるかを制御できず、接続を閉じる場所がない。
1 つの要求が複数のスレッドにまたがる場合（依存の準備と本体）に、別々の接続を使ってしまう。採用しない。

### 案 C: 保存ごとに専用のメソッドをリポジトリに足す（例: 判定結果と編集状態を一緒に保存する）

まとめる組み合わせが増えるたびに port が増える。まとめる・解除ではレクチャー・編集状態・ジョブ表の 3 つにまたがる。採用しない。

### 案 D: 動画のトークンを Cookie で渡す

URL にトークンが出ないが、同じマシンの別のポートで動くページからも Cookie が送られる（ポートは同一サイトの判定に含まれない）。
ヘッダーとクエリのほうが、送る場面をこちらで決められる。採用しない。

### 案 E: 動画を fetch で読み、blob の URL にして再生する

ヘッダーを付けられるが、動画の全体を先に読み込むことになり、長い録画でシークができるまで待たされる。採用しない。
