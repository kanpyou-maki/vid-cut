# ADR-004: ローカルアプリの実行形態（API サーバー + worker プロセス + SQLite）

**ステータス:** 承認済み
**作成日:** 2026-10-03

## Context（背景）

一括解析（US-10）では、画面から投入したジョブを順に処理し、進捗を表示し、失敗したものを再実行できる必要がある。
解析は 1 本あたり数分かかり、ML モデルが大きなメモリを使う。コマンドラインからも同じジョブを投入したい。
利用者は本人 1 名、動作環境はローカルの Mac 1 台。

## Decision（決定）

- `vidcut serve` が **API サーバー（FastAPI）** と **worker プロセス** を 1 つずつ起動する
- 両者の連携は **SQLite のジョブ表**だけで行う。worker はジョブを 1 件ずつ取り出して処理し、進捗を書き込む。画面は 1 秒間隔でポーリングする
- 起動時に `running` のまま残ったジョブは `queued` に戻す。パイプラインの各段は生成物を保存するので、再開すると完了済みの段は飛ばす
- ワークスペースは既定で `~/VidCut/`（環境変数 `VIDCUT_WORKSPACE` で変更可）
- メタデータ・ジョブ・編集状態は SQLite（標準ライブラリの `sqlite3`）、大きな生成物はワークスペースのファイルに保存する
- サーバーは `127.0.0.1` にだけ待ち受ける。投入するファイルは、サーバー側でフォルダを辿る簡易ブラウザ（ホームディレクトリ配下に限定）で選ぶ

## Consequences（結果）

### ポジティブ

- 外部のメッセージキューや DB サーバーが不要で、構成が単純
- ML の処理が API サーバーの応答を妨げない
- ジョブ表がそのまま進捗一覧と再実行の根拠になる

### ネガティブ

- ポーリングなので進捗表示に最大 1 秒の遅れがある（許容範囲）
- ブラウザの標準のファイル選択やドラッグ & ドロップは使えない（絶対パスが取れないため）

## Alternatives Considered（検討した代替案）

### 案 A: API サーバー内のスレッドで処理する

構成は最小だが、ML の処理中に API の応答が遅くなるおそれがあり、サーバーの再起動でジョブが失われやすい。採用しない。

### 案 B: Celery / RQ + Redis

1 人用のローカルアプリには過剰。採用しない。

### 案 C: ファイルをブラウザからアップロードする

ドラッグ & ドロップが使えるが、数 GB の素材をワークスペースへ複製することになる。採用しない（将来、併用は可能）。
