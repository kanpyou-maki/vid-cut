# ADR-006: frontend の土台（開発中のトークン・依存・画面の切り替え）

**ステータス:** 承認済み
**作成日:** 2026-10-04

## Context（背景）

M7 で画面（frontend）を作り始めるにあたり、次の 3 点を決める必要があった。

1. すべての `/api` はトークン（`X-VidCut-Token`）を求める（[ADR-005](./ADR-005-local-api-runtime.md)、[Design Doc](../design.md) 3-5-1）。
   トークンは `vidcut serve` が画面の HTML に埋め込むが、開発中は Vite の開発サーバーが HTML を配信するので、埋め込めない
2. 画面に足す依存を決める（API の呼び出し、画面の切り替え、データの取得、波形）
3. CSP は `default-src 'self'` で、外部の CDN・フォント・画像は使えない

## Decision（決定）

- **開発中のトークンは、Vite のプラグインが埋め込む。** プラグイン（`frontend/vite-plugins/devToken.ts`）は開発サーバーでだけ働き、
  HTML を返すたびに Node 側で backend の画面の HTML を読んで、`<meta name="vidcut-token">` を開発用の HTML に足す。
  画面のコードは、開発中も本番も同じ（meta 要素から読む）
- **backend は、ビルドの案内のページ（503）にもトークンを埋め込む。** 開発中は `frontend/dist` がないことがあり、そのときもプラグインが読めるようにする
- **開発サーバーの CORS は無効にする。** Vite の既定では、ほかの localhost のページが開発用の HTML（トークン入り）を読める
- **足す依存は `openapi-fetch` と `wavesurfer.js`（最新の安定版。8 系）だけにする。**
  画面の切り替え（2 画面）は History API の自作、データの取得は 1 秒間隔のポーリングの自作、並べ替えは上下のボタン、スタイルは素の CSS にする

## Consequences（結果）

### ポジティブ

- backend にトークンを返す経路（エンドポイント）が増えない。本番のコードに、開発用の分岐が入らない
- ビルドの出力にトークンが入らない（プラグインは開発サーバーでだけ働く）
- 依存が少なく、`npm audit` の対象と CSP の見直しの範囲が小さい
- API の型は生成済みの `schema.d.ts` をそのまま使うので、backend とずれればコンパイルで分かる

### ネガティブ

- backend を起動し直すとトークンが変わり、開いている画面は読み込み直しが要る（本番も同じ）
- 開発中は、backend を先に起動していないと画面が API を呼べない（画面に案内を出す）
- ビルドの案内のページにもトークンが入る。読める相手は通常の画面の HTML と同じ（Host・Origin の検査は同じ。同じ Mac のほかのプログラムは読める。Design Doc 3-5-1 の前提のまま）
- 画面の切り替えとポーリングを自分で持つ（どちらも小さいが、テストと保守はこちらの責任）

## Alternatives Considered（検討した代替案）

### 案 A: `--dev` のときだけトークンを返すエンドポイントを足す

画面が起動時に取りに行く。本番のコードに、トークンを返す経路ができる（`--dev` の判定を誤ると、ほかのページから読まれる）。採用しない。

### 案 B: 開発中はトークンの検査を外す

`--dev` の間、`/api/fs`（ホーム配下の一覧）がブラウザで開いたほかのページから読める。採用しない。

### 案 C: 開発の前に必ず `npm run build` をする（案内のページにトークンを入れない）

backend の変更が要らないが、手順が 1 つ増え、忘れると理由の分かりにくい 401 になる。採用しない。

### 案 D: ルーティングとデータ取得のライブラリ（react-router、TanStack Query）を入れる

画面は 2 つ、取得は数種類で、自作のほうが小さい。画面が増えたら見直す。採用しない。

### 案 E: 型を使わない自作の `fetch` の包み

`openapi-fetch` がしている「パスと引数と応答の型の対応づけ」を自分で書くことになる。採用しない。
